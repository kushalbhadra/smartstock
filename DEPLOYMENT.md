# Deployment

## Local container stack

The compose file builds the API and frontend and starts them with PostgreSQL
and Redis. From the backend directory, copy `.env.example` to `.env`, replace
every placeholder with unique values, then run:

```powershell
docker compose up --build -d
```

Open `http://localhost` (frontend) or `http://localhost:8080` (API). The
bootstrap administrator is created on the first startup only. The Compose
stack uses the `docker` Spring profile, which lets Hibernate create/update the
database schema for a self-hosted first run. Back up the PostgreSQL volume and
secure Redis and database access before exposing this stack to the internet.

## Production deployment

Build and deploy the API and static frontend as separate containers, or use
the Dockerfiles as the basis for the chosen hosting platform. Set
`SPRING_PROFILES_ACTIVE=prod` for the API, use managed PostgreSQL and Redis
with TLS, and set `SUPABASE_DB_URL`, `SUPABASE_USERNAME`, `SUPABASE_PASSWORD`,
`REDIS_URL`, `APP_CORS_ALLOWED_ORIGINS`, `JWT_SECRET`, and the bootstrap
administrator variables through the platform's secret manager. Set
`GROQ_API_KEY` only when AI forecasting is enabled. WhatsApp/Twilio delivery
is not part of the active application; alerts are stored as in-app
notifications. The production profile validates rather than mutates the
database schema; provision and verify the schema before rollout.
The frontend's `VITE_API_BASE_URL` is embedded at build time and must point to
the public HTTPS API URL.

Before deploying the in-app notifications feature with the production
`validate` profile, provision its table and indexes:

```sql
CREATE TABLE notifications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    recipient_id BIGINT NOT NULL REFERENCES users(id),
    type VARCHAR(40) NOT NULL,
    title VARCHAR(100) NOT NULL,
    message VARCHAR(500) NOT NULL,
    severity VARCHAR(12) NOT NULL,
    condition_key VARCHAR(160) NOT NULL,
    target_type VARCHAR(20) NOT NULL,
    target_id BIGINT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    read_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL,
    last_occurred_at TIMESTAMP NOT NULL,
    resolved_at TIMESTAMP,
    updated_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_notifications_recipient_condition
        UNIQUE (recipient_id, condition_key)
);
CREATE INDEX idx_notifications_recipient_recent
    ON notifications (recipient_id, last_occurred_at);
CREATE INDEX idx_notifications_recipient_unread
    ON notifications (recipient_id, read_at);
```

Apply the DDL through the organization's normal migration process and verify
the schema before deploying the application.

For an existing `notifications` table, apply this additive migration instead
of recreating the table. It preserves notification history:

```sql
ALTER TABLE notifications ADD COLUMN IF NOT EXISTS title VARCHAR(100);
ALTER TABLE notifications ADD COLUMN IF NOT EXISTS severity VARCHAR(12);

UPDATE notifications
SET title = CASE type
        WHEN 'LOW_STOCK' THEN 'Low stock'
        WHEN 'OUT_OF_STOCK' THEN 'Out of stock'
        WHEN 'OVERSTOCK' THEN 'Overstock'
        WHEN 'WAREHOUSE_NEAR_CAPACITY' THEN 'Warehouse nearing capacity'
        WHEN 'WAREHOUSE_CAPACITY_FULL' THEN 'Warehouse at capacity'
        WHEN 'WAREHOUSE_CAPACITY_EXCEEDED' THEN 'Warehouse capacity exceeded'
        WHEN 'FORECAST_ANOMALY' THEN 'AI forecast anomaly'
        WHEN 'PURCHASE_ORDER_APPROVED' THEN 'Purchase order approved'
        WHEN 'PURCHASE_ORDER_PARTIALLY_RECEIVED'
            THEN 'Purchase order partially received'
        WHEN 'PURCHASE_ORDER_RECEIVED' THEN 'Purchase order received'
        ELSE 'Inventory notification'
    END
WHERE title IS NULL;

UPDATE notifications
SET severity = CASE
        WHEN type IN ('OUT_OF_STOCK', 'OVERSTOCK',
                      'WAREHOUSE_CAPACITY_FULL',
                      'WAREHOUSE_CAPACITY_EXCEEDED') THEN 'CRITICAL'
        WHEN type IN ('LOW_STOCK', 'WAREHOUSE_NEAR_CAPACITY',
                      'FORECAST_ANOMALY') THEN 'WARNING'
        ELSE 'INFO'
    END
WHERE severity IS NULL;

ALTER TABLE notifications ALTER COLUMN title SET NOT NULL;
ALTER TABLE notifications ALTER COLUMN severity SET NOT NULL;
```

The current inventory workflow also adds product storage factors, supplier
codes/contact details/active status, movement history snapshots,
purchase-order receiving fields, and receipt records. Apply these
additive PostgreSQL statements before deploying that backend version:

```sql
ALTER TABLE products
    ADD COLUMN IF NOT EXISTS storage_capacity_factor NUMERIC(12, 4)
        NOT NULL DEFAULT 1;

ALTER TABLE suppliers
    ADD COLUMN IF NOT EXISTS supplier_code VARCHAR(40),
    ADD COLUMN IF NOT EXISTS contact_person VARCHAR(150),
    ADD COLUMN IF NOT EXISTS address VARCHAR(500),
    ADD COLUMN IF NOT EXISTS active BOOLEAN NOT NULL DEFAULT TRUE;

CREATE UNIQUE INDEX IF NOT EXISTS uk_suppliers_supplier_code
    ON suppliers (supplier_code)
    WHERE supplier_code IS NOT NULL;

ALTER TABLE stock_movements
    ADD COLUMN IF NOT EXISTS previous_quantity INTEGER,
    ADD COLUMN IF NOT EXISTS new_quantity INTEGER,
    ADD COLUMN IF NOT EXISTS reference_number VARCHAR(120),
    ADD COLUMN IF NOT EXISTS source_warehouse_id BIGINT
        REFERENCES warehouses(id),
    ADD COLUMN IF NOT EXISTS destination_warehouse_id BIGINT
        REFERENCES warehouses(id);

ALTER TABLE purchase_orders
    ADD COLUMN IF NOT EXISTS purchase_unit_price NUMERIC(12, 2)
        NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS received_quantity INTEGER
        NOT NULL DEFAULT 0;

CREATE TABLE IF NOT EXISTS purchase_order_receipts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL REFERENCES purchase_orders(id),
    quantity INTEGER NOT NULL,
    received_date DATE NOT NULL,
    reference_number VARCHAR(120) NOT NULL,
    notes VARCHAR(500),
    received_by BIGINT NOT NULL REFERENCES users(id),
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_po_receipt_reference
        UNIQUE (purchase_order_id, reference_number)
);
```

Existing purchase orders retain their quantities; `received_quantity` starts
at zero because historical receipt breakdowns are not available. Existing
orders also receive a zero unit-price placeholder until corrected by an
operator. Do not remove the defaults until all existing rows are backfilled.

Terminate TLS at the hosting platform or reverse proxy. Restrict CORS to the
exact HTTPS frontend origin(s), configure database backups and restore
practice, rotate bootstrap and JWT secrets, and do not publish `.env` files.
The policy pages are starter drafts and require organization-specific legal
review before production use.
